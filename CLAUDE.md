## Overview

`SAP_DM_DQ` is a memory-augmented agent for SAP data migration / data-quality profiling. It profiles tables statistically, has an LLM propose pandas checks, runs those checks locally in a sandbox, has an LLM judge the results, and lets a human approve/reject findings through a review UI before they are promoted into a reusable skill library.

Two independently runnable components:
- `explorer_agent/` — the LangGraph-based profiling/exploration pipeline (CLI).
- `review_app/` — a FastAPI + vanilla JS app for human review of findings and skill promotion.

### Data in this repo

- `client_data/<client_id>/` is the working copy of each client's uploaded data (see Review app). Locally it holds the **synthetic** test client `acme-retail` (the vendor-only clients were removed). Each has `Data_Dictionary.csv`, table CSVs and `workspace.json`. Answer keys list the seeded defects (`Object,Table,Key_Field,Key,Org_Key,Field,Issue_Type,Issue_Description`). When you change a dataset, update its answer key in the same change. 
- **Answer keys live one level above the client folders**, as `client_data/<client_id>{_,-}{ANSWER_KEY,Answer_Key}.csv` (the naming is inconsistent). Never put one inside `client_data/<client_id>/`. `data_loader.discover_table_files` treats every CSV under `--data-dir` as a table, recursively, except the dictionary. A key inside the client folder would be profiled as table `ANSWER_KEY` and sent to the planner LLM, leaking the answers into the run. Runs are safe because the review app always passes `--data-dir client_data/<client_id>`. Pointing a CLI run at `client_data/` itself also fails, because every client has an `LFA1.csv` and discovery refuses two files with the same table name.
- **Not in git:** `client_data/`, `episodic_memory.db`, `handoff/`, `logs/` and `memory_store/` are gitignored and untracked (since 2026-09-24): client data, run history and agent state stay on the machine that produced them. A fresh clone therefore has no synthetic client, answer key or run history - copy them in separately. Older commits still contain the synthetic `client_data/` files and an `episodic_memory.db`; removing them from history would need a history rewrite. Real client data must never be committed.
- `explorer_agent/evaluate.py` is a **minimal scoring harness**: it matches a run's finding rows to the answer key on table + object key + field and prints recall per issue type and precision per finding. It is not wired into CI. The synthetic keys are incomplete: they miss real defects the generators produced (e.g. 11-character "GSTINs" and `FR`+8-digit "VAT numbers" in the vendor-only clients), so low precision on a rule means "read the rows", not "the rule is wrong".

### Configuration

`explorer_agent/config.py`'s `Config` class is the single place every module reads settings from. It layers two sources:
- **`config.yaml`** (project root) — non-secret, shareable defaults: LLM provider/model, data settings (default dictionary file name, per-client upload folder — tables are discovered from files, not listed), duplicate-matching rules, sandbox limits, memory/log/DB paths, cache thresholds, etc. Committed to version control.
- **`.env`** (outside the repo: the file named by `env_file` in `config.yaml`, default `~/.env` = the user's home directory; `EXPLORER_ENV_FILE` overrides; falls back to `<project>/.env` with a warning if missing) — secrets only (`GEMINI_API_KEY`, etc.). The local GGUF path is `llm.local.model_path` in `config.yaml` (`~` expanded; `EXPLORER_LOCAL_LLM_MODEL_PATH` still overrides). Any `config.yaml` value can also be overridden per-machine by the matching environment variable (see comments in both files for exact names).

All relative paths (`EPISODIC_DB_PATH`, `LOG_DIR`, `MEMORY_BASE_DIR`) are resolved against `Config.PROJECT_ROOT`, not the process's current working directory, so behavior doesn't depend on which directory a script is launched from.

### LLM provider (`explorer_agent/llm_providers.py`)

Exactly one backend, **no fallback chain**: `Config.LLM_PROVIDER` (`llm.provider` / `--llm-provider`) is `google` (Gemini) or `local` (GGUF). `build_llms()` builds that model and returns an `LLMBundle` of planner / reflector / duplicate-rule / column-mapping runnables. Transient errors are retried inside the provider SDK (`llm.max_retries`); malformed/missing structured output is retried on the same model (`llm.structured_output_retries`); any remaining failure raises `LLMChainExhaustedError`: `main.py` skips that table (exit code 1) and `cache_runner.py` falls back to its rule-based heuristic. `metrics.llm_call_failures` counts failures. `Config.validate()` requires the credentials (`GEMINI_API_KEY`) or model path for the selected provider. Callers (`graph.py`, `cache_runner.py`) just call `.invoke()`. Groq was removed; a provider outage now means skipped tables, not a silent switch to a weaker model (the Groq qwen fallback mapped columns noticeably worse).

The local model is loaded lazily (`llm_providers._get_local_llm()`) and only when `llm.provider` is `local`; provider SDKs are imported per provider, so importing `explorer_agent.main` never pulls `llama_cpp` into memory.

## Architecture

### Tri-tier memory system

This is the central design concept and spans several files — understand it before changing any memory-related code:

1. **Episodic memory** (`explorer_agent/episodic_store.py`) — SQLite (`episodic_memory.db`). Every run and every finding (plus row-level `finding_items` detail) is logged here first, along with human review status (`PENDING`/`APPROVED`/`REJECTED`). This is the append-only history and the human-in-the-loop gate.
2. **Procedural memory** (`explorer_agent/memory/skill_registry.py`) — JSON registry (`memory_store/procedural/skill_registry.json`) + one `.py` file per skill. This is the **source of truth** for promoted, reusable checks — human-readable and auditable.
3. **Semantic memory** (`explorer_agent/memory/chroma_store.py`) — ChromaDB vector index, embedded locally with all-MiniLM-L6-v2 (Chroma's ONNX export via onnxruntime; no API calls, never Hugging Face — model files resolve from `memory.embedding.model_dir` → a Kaggle handle via kagglehub → Chroma's cache/S3 download). The collection's metadata records the embedding model; on mismatch it is dropped and `memory/__init__.py:get_memory_store()` rebuilds it from the registry. This is a **derived search index built from procedural memory**, never the other way around. If it's lost or corrupted, `explorer_agent/memory/reindex.py` rebuilds it entirely from the JSON registry.

Promotion (`explorer_agent/memory/promotion.py`) is the pipeline that moves data episodic → procedural → semantic. It only promotes findings that are (a) human-APPROVED via the review app, (b) marked `reusable` by the LLM's own judgment, and (c) have captured `check_code`. It also does near-duplicate detection against existing skills (vector distance threshold) before creating a new skill entry, to avoid redundant near-identical skills.

**Backend abstraction rule**: no module outside `explorer_agent/memory/chroma_store.py` may import `chromadb` directly. Everything goes through the `MemoryStore` ABC (`explorer_agent/memory/base.py`) so swapping vector backends means writing one new adapter class (see `explorer_agent/memory/__init__.py`'s `get_memory_store()` factory), not touching `promotion.py`/`retriever.py`/`main.py`.

`explorer_agent/memory/retriever.py` (`SkillRetriever`) is a separate layer on top of the generic `MemoryStore.search()` — it knows how to build a query from table/column/dtype/business-meaning and format results for prompt injection as *hints*, distinct from `skill_registry.get_skills_for_table_column()`'s exact-match lookup used by the cache fast path.

### Token usage (`explorer_agent/llm_usage.py`)

Every structured LLM request is measured: `llm_providers._structured_chain` attaches a `UsageCollector` callback that reads the token counts the provider already returns (Gemini via LangChain `usage_metadata`; the local GGUF via llama.cpp's `usage`). Each request is logged (`[planner] google:... tokens in=3,482 out=6,325 (thinking 3,319) ...`), added to `metrics.llm_*_tokens`, and stored as one row in SQLite `llm_calls` (`run_id`, `table_name` (NULL for client-wide column mapping), `role`, model, input/output/reasoning/total tokens, seconds, success). Counts only: no prompt or response is stored, so the privacy boundary is unchanged. **Thinking tokens are part of the output count** (Gemini bills them as output) and dominate: a trivial "reply ok" call was 8 in / 93 out, 88 of them thinking. A structured-output retry is a second billed request, so `metrics.planner_llm_calls` (one per table) understates cost; the token rows are the truth. Read it at `GET /api/runs/{run_id}/llm-usage` (totals, per role, per call), `llm_usage` on every entry of `GET /api/runs`, the `profiling.completed` event and `RESULT_JSON`, the CLI's "LLM tokens" line, and the token line beside the run selector on the review page. No prices on purpose (they change and are the user's to enter). Records are buffered until the run row exists (`usage.set_run`), because column mapping runs first.

### Pre-flight checks (`explorer_agent/preflight.py`)

Before a planner check reaches the sandbox, `check_executor.execute_checks` parses its `code` with `ast` against the real tables, at zero LLM cost. It rejects code that doesn't parse or never sets `result`; reads a column that isn't in the table (with a case hint) or a table that isn't loaded; uses `.str` on a numeric column; averages or compares a text column with a number; or calls a string method inside `.apply(lambda ...)` on a column that has empty cells (the NaN crash seen in production logs). It is conservative: when the code rebuilds `df` the column check is skipped. A rejected check returns `success: False` with an `error` starting `Pre-flight:` that says what to change, and counts in `metrics.preflight_rejected`; `detail_code` problems only log a warning. A rejected check is fed to the repair loop (below) with this message as its error; with repair off (`max_repair_rounds: 0`) it is simply dropped. Dtypes already reflect the data dictionary, because the loader types measure columns from it.

### Explorer graph (`explorer_agent/graph.py`)

A LangGraph `StateGraph` (linear except one bounded repair loop, see below) run once per table via `explore_table()` in `main.py`:

1. `plan_batch` — ONE LLM call (`planner_structured`, `.with_structured_output(CheckPlan)`) proposes a batch of pandas checks for the whole table at once, from a privacy-sanitized statistical profile (never raw data). Tables over `profiling.sample_rows` (50k) are profiled on a fixed-seed random sample (`profiling.sample_seed`), and the prompt says so: counts refer to the sample, ratios estimate the table. The checks themselves and every deterministic engine run on all rows.
2. `execute_all` — all proposed checks run locally in the sandbox, zero LLM involvement. Then a conditional edge (`route_after_execute`): while some checks failed and `repair_round < Config.MAX_REPAIR_ROUNDS`, go to `repair_batch`; otherwise on to `reflect_batch`.
3. `reflect_batch` — ONE LLM call (`reflector_structured`, `.with_structured_output(ReflectionBatch)`) judges all check results at once (severity/confidence/reusability), then row-level `detail_rows` are extracted locally (via `detail_code`) only for CONFIRMED findings.
4. `finalize` → `human_review` (stub node; actual human review happens later in `review_app`).

**Repair loop** (`repair.py`, `graph.py`, `profiling.max_repair_rounds`, default 1, 0 = off; `--max-repair-rounds`; the Run dialog's "Repair rounds"): the only cycle, `execute_all → repair_batch → execute_all`. `repair_batch` sends every failed check (sandbox error or pre-flight rejection) back to the planner in ONE call (`CheckRepair` schema, usage role `repair`) with its code, hypothesis, the table's column names/dtypes and a one-line error; only the rewritten checks re-run and every other result is kept. A repair replaces only `code`/`detail_code` (column, category, scope stay as planned). The loop ends on the counter, never on the model, and also when a repair changes nothing or the repair call fails (the table then continues with the checks that ran, it is not skipped). Sandbox error text can echo a value, so it is reduced to one line and every quoted token becomes `'<value>'` unless it is a column/table name, a Python/pandas attribute or type name, or punctuation (an allow-list, best effort like `privacy_guard`); pre-flight messages are generated locally from column names and dtypes and pass as they are. `metrics.repair_llm_calls` / `checks_repaired` count it. Not built: sending back checks that ran but flag 0 % or ~100 % of rows (needs a threshold decision).

This design intentionally costs exactly 2 LLM calls per table regardless of column count (plus, only the first time a client's table layout is seen, one call to draft its duplicate-matching rules — see below) (contrast with an earlier per-column tool-calling design referenced in the module docstring).

Each `ProposedCheck` (`explorer_agent/schemas.py`) has two code fields: `code` (must set an AGGREGATE `result` — this is what gets sent to the reflector LLM) and optional `detail_code` (sets `detail_rows`, a list of offending rows for local human review only — **never sent to any LLM**).

### 4-pillar classification and duplicate governance

Every `ProposedCheck` and `FindingJudgment` (`explorer_agent/schemas.py`) also carries a classification, produced by the same planner/reflector LLM calls (no extra calls):

- **`category`** — `ACTIVENESS` / `DUPLICATE` / `COMPLETENESS` / `CORRECTNESS`, the four profiling pillars.
- **`rule_scope`** — `UNIVERSAL` / `INDUSTRY_SPECIFIC` / `CLIENT_SPECIFIC`, a 3-tier scope for how broadly a check generalizes (invalid values fall back to `UNIVERSAL`/`CORRECTNESS` via `field_validator`s, never raise).
- **`fix_type`** (`AUTO_FIXABLE` / `MANUAL_FIX`) + `auto_fix_value` — mainly for `COMPLETENESS` findings.
- **`is_anomaly`** — statistical outlier flag.
- **`duplicate_fields`** — for `DUPLICATE`-category checks, the fields used for match logic (e.g. `["NAME1", "PSTLZ", "STCD1"]`).

**Duplicate matching is deterministic; the rules it executes are written by the LLM once per client and schema.** `explorer_agent/duplicate_detector.py` does the matching for **any** table with zero LLM involvement, but nothing in it decides what a column means. That spec comes from `explorer_agent/duplicate_rule_planner.py`: ONE structured call (`DuplicateRulePlan`, `schemas.py`) that sees only metadata — column names, the client's data dictionary text, aggregate statistics and masked example values (`mask_value`, last two characters) — and gives every column a role (`KEY` / `IDENTIFIER` / `NAME` / `LOCATION` / `CONTEXT` / `IGNORE`, plus `identifier_group` for composites like bank country + key + account, `key_unique`, `label`, `rule_scope` and a one-sentence `reason` per column). `compile_plan` turns that into the same rules dict the detector has always executed (`key`/`key_unique`/`name`/`identifiers`/`location`/`display`/`label`/`why`/`checks`), dropping columns the model invented and rejecting any single-column identifier whose filled values are less than `duplicates.rules.min_identifier_distinct` distinct (arithmetic, not semantics: such a value covers many records — it catches a composite identifier whose parts were left ungrouped). The reasons land in `rules["why"]`, shown by "View Matching Rules" (`describe_rules`), so the review UI now shows the model's own justification per column.

Why the LLM and not Python: a (TABLE, COLUMN) pair does not mean the same thing at every company — standard fields get repurposed, Z-fields mean whatever their owner decided, and uploads may not be SAP at all. The previous regex/keyword inference in `duplicate_rules.py` assumed otherwise and was removed; that module is now only the resolver.

**Resolution order** (`duplicate_rules.resolve_rules`): `config.yaml` → `duplicates.tables.<TABLE>` (manual pin) → rules saved for **this client** whose schema signature matches → shared `UNIVERSAL`/`INDUSTRY_SPECIFIC` rules (only with `duplicates.rules.reuse_across_clients`, exact signature) → one LLM call, then saved. `explorer_agent/memory/duplicate_rule_store.py` keeps them as human-readable JSON: `memory_store/clients/<client_id>/duplicate_rules.json` and `memory_store/procedural/duplicate_rules.json`, keyed by a **schema signature** (table name + hash of its column set, order/case independent). So the first run for a client costs one call per table and every later run costs none; a table whose columns changed is re-drafted alone (even if the columns its rules use all survive — a new column may itself be worth matching on), the rest stay free. Cross-client reuse is off by default for the meaning-divergence reason above. `metrics.duplicate_rule_llm_calls/hits/misses` report this per run. If rules can't be produced (no LLM configured for `--duplicates-only`, or every model failed), the table falls back to **identical rows only** — comparing whole rows needs no business knowledge, so it cannot be wrong, whereas guessing roles in Python would be. Every table is checked for identical rows anyway. `main.py` builds the planner lazily (`RulePlanner`) so a run served entirely from memory never constructs an LLM, passes the run's dictionary and client, and runs detection for every table before the planner (its findings are saved even if the LLM chain fails). The planner prompt forbids DUPLICATE checks and `graph.py` discards any it proposes; the finding's `category` always comes from the planner's check, never the reflector's default (that override once stored a KOINH completeness check as a DUPLICATE finding). Matching: a shared identifier → `EXACT`; same normalized name + ≥2/1 matching location fields → `EXACT`/`PROBABLE`; fuzzy name ≥ `fuzzy_name_threshold` with a matching location field → `PROBABLE` (≥90%) / `SIMILAR`; same name elsewhere → `SIMILAR`. Normalization is column-wide (vectorized, same steps as the per-value `normalize_text`/`_normalize_identifier`, one shared `_NORMALIZE_STEPS` list) and the full record (display values, record id) is built only for rows in a candidate pair, which keeps 1M rows at ~2 GB instead of one dict per row. Guards: candidate pairs come from identifier/name/location blocking (no row-order window), names whose numbers differ never fuzzy-match, placeholder identifiers (`INVALID…`, `N/A`, `0000…`) are ignored, and any identifier or name shared by more than `max_identifier_share` keys is treated as a placeholder. Rows with the same business key (e.g. two LFBK accounts of one vendor) are never linked. `profiler_primitives.cluster_duplicates` (still injected into the sandbox, with `fuzzy_token_similarity` and `detect_distribution_outliers`) is a thin wrapper over the detector for old check code and cached skills.

**Clients and remembered decisions.** Every run belongs to a client (company): `--client` / the Run dialog's required field → `runs.client_id` (slug, e.g. `acme-retail`) + `client_name`. `explorer_agent/client_knowledge.py` keeps per-client knowledge as human-readable JSON under `memory.clients_dir` (`memory_store/clients/<client_id>/client.json`, `duplicate_decisions.json`, and `duplicate_rules.json` written by `memory/duplicate_rule_store.py`) — durable knowledge next to procedural memory, not per-run episodic state. Duplicate decisions are stored per record keyed by `record_id` = `<key>|<sha1 fingerprint of record_data>` with the partner record_ids it was grouped with. The review app writes them the moment a row/group verdict is saved (`_remember_duplicate_groups` in `review_app/main.py`; last action wins, `PENDING` removes). On the next run for that client, `duplicate_detector` skips a pair only when **both** records were marked `UNIQUE` against each other — reviewers mark `DUPLICATE` + `UNIQUE` to mean "this is the duplicate, that is the original", so a single `UNIQUE` must not hide a confirmed duplicate — and pre-fills any remembered verdict (`finding_items.decision_source = 'REMEMBERED'`, shown as ↺ in the UI) when a record is grouped with a former partner again. Because the fingerprint is part of the id, any change to a record's display fields makes its old decisions stop applying. Runs created before clients existed can be linked once via `POST /api/runs/{id}/client`, which also saves decisions already made in them; `/api/findings` and `/api/runs` accept `client_id`, `/api/clients` lists clients. The review dashboard is always scoped to exactly one client (there is no "all clients" view): page 2's `?client=` drives the runs list, findings, tab counts and status chips, and the client can only be changed on page 1 (see "Review app" below); the last client is kept in `localStorage` to preselect it on page 1.

Each duplicate row in `finding_items` carries `duplicate_group_id`, `similarity_score`, `match_type` (`EXACT`/`PROBABLE`/`SIMILAR`), `match_reasons`, and `record_data` (JSON of the table's `display` columns, used for the side-by-side comparison), plus the survivorship fields below (`quality_score`, `score_breakdown`, `recommended_verdict`, `suggested_action`, `is_golden_record` = the chosen golden record, `reviewer`, `undo_state`). Each row also tracks its own human review state, separate from the finding-level `PENDING`/`APPROVED`/`REJECTED` status: `review_verdict` (`PENDING`/`DUPLICATE`/`UNIQUE`/`TO_BE_CONFIRMED`).

**Survivorship and the Accept flow** (`explorer_agent/survivorship.py`, config `survivorship.*`). After the rules run, every member of a duplicate group gets a 0–100 `quality_score` from four components, each 0..1, read through the column mapping: **completeness** (important mapped fields filled *and* not flagged by a Priority 1/2 rule on that row, so `TBD` is not a tax number), **active** (1 / 0.5 if blocked / 0 if marked for deletion), **usage** (share of org-level child tables the record is extended to; the record the business uses survives), and **recency** (creation date ranked *within the group*). Weights default to 0.4/0.25/0.2/0.15. A component that can't be computed is dropped and the rest re-weighted, and with nothing to score on (e.g. `--duplicates-only`) there is no recommendation. The best record is the **recommended golden record** (the survivor: `recommended_verdict` UNIQUE, `suggested_action` GOLDEN_RECORD). The others are recommended DUPLICATE with `MERGE_INTO <key>` when they have org-level data to move, else `BLOCK_AND_DELETE`. A survivor remembered from an earlier review wins over the score. SIMILAR groups (look-alikes) get scores but no pre-selection (`CONFIRM_DUPLICATE_FIRST`). It is **only a pre-selection**: `review_verdict` stays PENDING until a reviewer acts. On acme it matched the key's "Golden Record Survivor" in 32/33 groups (the 33rd is SIMILAR, 0 wrong), and the spec's original 0.5/0.3/0.2 formula without usage scored the same on this data. In the UI each record has **★ Golden record** (the survivor, UNIQUE), **Unique** (a separate entity, i.e. a look-alike, also UNIQUE) and **Duplicate** (of the golden record, the default for everything not marked). Drafts are local until the cluster's **Accept** (`POST /api/findings/{id}/duplicate-groups/{group_id}/accept`, `episodic_store.accept_cluster`: survivor + `separate_item_ids` + `reviewer`; "no survivor" is only valid when every record is Unique). **To be confirmed** is cluster-level only (`/verdict` with `TO_BE_CONFIRMED`). Either action **locks** the cluster in the UI, and a circular **↺** undoes it (`POST .../duplicate-groups/{group_id}/undo`, `episodic_store.undo_cluster`). Before each cluster action the rows' review state is snapshotted into `finding_items.undo_state`, so undo restores exactly the earlier state, including remembered pre-fills (one level), and re-syncs the client's memory. `get_duplicate_groups` returns `recommended_survivor_id` and `accepted_as_recommended`, the online quality signal the UI shows as "recommendation kept in n/m". The reviewer name is free text kept in `localStorage`, with no SSO.

**Decided groups are not shown again** (`duplicates.hide_decided_groups`): detection still runs every time (it's free), but a group where *every* record already has a remembered DUPLICATE/UNIQUE decision covering all its current partners (`client_knowledge.is_settled_group`) is dropped before saving, and the finding summary says how many. A new record joining the group, or a changed record (new fingerprint), brings it back with the known verdicts pre-filled. TO_BE_CONFIRMED groups keep coming back. The remembered decisions also hold `survivor`, `merge_into`, `action`, `recommended_verdict` and `reviewer`, and `GET /api/clients/{id}/duplicate-decisions.csv` exports them across all runs as the **merge map** (old number → surviving number + action) for the future cleansing/load stage. The review app also exposes `/api/findings/{id}/duplicate-groups` (rows grouped by `duplicate_group_id` with parsed `record` data and verdict counts) and `/api/finding-items/{id}/verdict` (per-row verdict, still used for non-duplicate pillars). Finding cards show row review progress (`item_count`/`reviewed_count`/`group_count` from `get_findings_light`). `/api/findings` and `/api/stats` accept `category`/`rule_scope` filters for the classification breakdown, and `/api/finding-items/{id}/autofill` applies `auto_fix_value` for `AUTO_FIXABLE` `COMPLETENESS` rows.

### Column mapping (`explorer_agent/column_mapping.py`)

The deterministic engines below are written against **business concepts**, never column names: `KEY`, `ORG_UNIT`, `DELETION_FLAG`, `BLOCK_FLAG`, `CREATED_DATE`, `COUNTRY`, `POSTAL_CODE`, `TAX_ID`, `LEGAL_NAME`, `EMAIL`, `PHONE`, `AMOUNT`, `QUANTITY`, `CURRENCY`, `CODE`, `TEXT`, … (`schemas.ColumnConcept`), plus per-column attributes (`part_of_key`, `references` = `TABLE.COLUMN` for orphan checks, `related_column` = the COUNTRY of a postal code/tax id or the CURRENCY of an amount, `required`/`required_group`, `flag_set_values`, `block_type`, `cascades`, `allow_negative`, `reason`). `resolve_mappings` maps **every loaded table before any rule runs** (rules on one table read others' mappings), in this order:

1. Saved for this client with a matching schema signature: `memory_store/clients/<client_id>/column_mappings.json`. Human-readable, and **the correction path**: a reviewer edits it, and later runs reuse it at zero LLM cost.
2. SAP standard: when every uploaded column of the table is listed under `standard_columns` in the rule pack. Free, not saved, so pack updates apply at once. A `dictionary_override` there lets the client's dictionary text change an attribute (acme/danawsiv document LFA1-SPERM as a *posting* block, so block propagation targets LFB1-SPERR rather than LFM1-SPERM).
3. Otherwise **one LLM call per table** (`ColumnMappingPlan`, `llm_providers.column_mapping_structured`), from metadata only: dictionary text, the `column_metadata` statistics and masked samples shared with the duplicate planner, `short_code_values` (at most 5 distinct values of 1–2 characters, so the model can say which flag value means "set"), and `value_overlap` (the share of a column's distinct values found in a unique column of another table that has MORE distinct values, which is evidence for `references`). `compile_plan` then applies an arithmetic safety net: unknown columns and references dropped, a "flag" with more than 5 distinct values demoted to OTHER, a one-value flag's set value filled, and `references` filled when the model left it empty and ≥90% of values sit in the best candidate parent. `_apply_structure` (freshly LLM-mapped tables only) removes `part_of_key` from values, flags and text, clears `cascades` on tables nobody references, and defaults a referenced table's DELETION_FLAG to `cascades`. Every correction is appended to the column's `reason`.
4. No LLM, or all models failed: the known standard columns are mapped, the rest stay OTHER, and rules needing them are skipped.

Each rule finding's `check_code` ends with "Column meaning" lines: the columns it used, their concepts and reasons. That is where a reviewer sees what the mapping decided. `metrics.column_mapping_standard/hits/llm_calls/failures` report the source. Measured on a renamed copy of danawsiv (every table and column renamed, flags coded `Y`, dictionary still naming LFA1): gpt-oss-20b mapped every concept correctly; rule recall was 0.70 against 0.82 on the SAP-named original, with the gap in *judgment* attributes (which fields are required, whether a central block cascades). After four edits to `column_mappings.json`, recall was 0.87 with no LLM call.

### Deterministic SAP rule pack (`explorer_agent/sap_rules.py`) and anomalies (`explorer_agent/anomaly_rules.py`)

Known SAP standards are **data, not LLM output**. `explorer_agent/rule_packs/sap_master_data.yaml` (`sap_rules.pack_file`) holds the SAP-standard column mapping plus domain knowledge: ISO countries and currencies, postal and tax formats by country, text-hygiene patterns. `sap_rules.run_sap_rules` executes the Priority 1 families and `anomaly_rules.FAMILIES` (Priority 2) per table with **zero LLM calls**, right after duplicate detection and before the planner, so their findings survive an LLM outage and `--deterministic-only` runs them without any planner/reflector. Shared plumbing (`Ctx`, `RuleCoverage`, `finding`, `load_pack`) lives in `rule_context.py`. One finding per rule and table with every offending row (`reusable=False`, `rule_scope=UNIVERSAL`, `check_code` starts with `# Built-in SAP rule <id>`):

- **ACTIVENESS**: `DELETION_FLAG`/`BLOCK_FLAG` set (severity LOW, since a flag is a scoping fact, not an error); **dormancy** = `CREATED_DATE` older than `dormant_after_years` **and** no row in any child table that references the record and has an `ORG_UNIT` in its key (LFB1/LFM1, KNB1/KNVV, MARC/MBEW/MVKE). A creation date alone never means inactive; without transaction data this is the best evidence.
- **COMPLETENESS**: `required` columns blank (`required_group` = any one filled is enough, e.g. BANKN/IBAN). All `MANUAL_FIX` unless `sap_rules.client_overrides.<client>.auto_fix` agrees a default. Only SAP-standard mandatory fields are in the pack (KOINH is not); client requirements go in `client_overrides.<client>.mandatory`.
- **CORRECTNESS**: ISO country keys (case-sensitive: `de` fails on load); `POSTAL_CODE` against its country's format; **all `TAX_ID` columns of a row evaluated together**. A row is "missing" only when none holds a real value, and each filled value must match its country's formats (EU VAT + national), so a blank STCD1 is never an error on its own. Unknown countries are skipped, never failed.
- **RELATIONSHIP_INTEGRITY**: orphans (a `references` value missing in the referenced table; skipped when that table isn't loaded, e.g. `--tables LFB1`), and a master flag with `cascades` not carried to a child flag of the same concept and `block_type` (central deletion flag → LFB1/LFM1; MARA-LVORM does not cascade, and bank data on deleted vendors is not flagged).
- **Priority 2 anomalies** (`anomalies.*` in config.yaml): negative `AMOUNT`/`QUANTITY` (unless `allow_negative`); outliers on an **IQR fence over log10 values**, at least `outlier_min_fence_decades` wide, per currency, high side only by default. A linear 1.5×IQR on MINBW {0…2 500} would flag every 2 500 order. **Rare codes** in `CODE` columns (used ≤2× where the typical code covers many rows). Codes are keys, never numbers: ZTERM `0030` is not 30 days, that lives in T052. ISO 4217 currencies (case-sensitive). Text hygiene on `LEGAL_NAME`/`TEXT`/`STREET`/`CITY`: illegal characters (HTML entities excluded), unbalanced brackets, mojibake, HTML entities, leading or doubled spaces (trailing blanks are dropped by SAP CHAR fields), placeholders, and all-caps values in a mixed-case column. E-mail format (Unicode domains are valid, `..` is not) and phone format. `profiler_primitives.detect_distribution_outliers` still exists for sandboxed LLM code, but the planner prompt no longer points it at ZTERM.

Meaning divergence is handled by configuration and the mapping, not code: `sap_rules.disabled_rules` / `client_overrides.<client>.disabled_rules` (an id or a prefix like `flag`, `tax.LFA1`, `text.casing`), `dictionary_override` in the pack, and the editable saved mapping. `run_sap_rules` returns a `RuleCoverage`: its `lines` go into the planner prompt (rule descriptions only, never data, plus the columns no rule touches), and `graph.py` **drops planner checks whose (column, category[, sub_type]) a rule already covers**, because models ignore the prompt instruction (observed: re-proposed LOEVM/ERDAT/LAND1/AKONT checks, one suggesting to auto-fill AKONT). `metrics.sap_rules_evaluated/sap_rule_findings/anomaly_findings/sap_rule_rows/planner_checks_covered_by_rules` report this.

### Composite DQ scorecard (`explorer_agent/scorecard.py`)

Per table, migration object and run, computed **during the run** from the table (after value mapping), its column mapping, the rules' `RuleCoverage` and findings (`raw_tool_result.rows_flagged` is the uncapped count) and duplicate detection. Never computed from stored findings (capped rows, no denominators), and **LLM findings are excluded** so the index is reproducible. Pillars: **completeness** = filled mandatory cells / mandatory cells (a `required_group` counts as one cell, all tax fields as one); **correctness** = 1 − defective cells / non-blank cells of the columns a correctness rule checked (a composite check counts one cell per row); **uniqueness** = 1 − redundant records / records (group members beyond the survivor from EXACT/PROBABLE groups, reviewer DUPLICATE verdicts once decided, **plus groups settled in earlier runs and no longer shown**, counted from memory in `duplicate_detector.LAST_STATS[...]["settled_duplicates"]` as members minus kept UNIQUE records because identical rows share one record id; SIMILAR counted only as "possible"); **activeness** = not deleted and not dormant / records (blocked reported, not deducted). **DQ Index** = weighted mean of the pillars that have a score (`scorecard.weights`, default completeness 0.35 / correctness 0.35 / uniqueness 0.30 / **activeness 0**, since deleted/dormant is migration scope, not bad data). Objects come from the rule pack's `objects` (by the SAP tables a table maps to, else the upload sub-folder) and aggregate by summing numerators/denominators. Stored in SQLite `scorecards` (one row per table/object/run with a JSON `details`), served at `GET /api/scorecard?client_id=&run_id=` (+ `bands`, `weights`, previous run's index per entry for the trend), included in the `profiling.completed` event (`dq_index`, `scorecard_url`), and shown as a collapsible panel above the findings (hero index, status band icon+label from `scorecard.bands`, one meter per pillar with counts on hover, objects expandable to tables). Verified by hand on danawsiv (LFB1 completeness 64/3369, LFA1 redundant 69) and after accepting every recommendation (still 69, not 0).

**Record readiness is the headline** (the cell-based index sits near 100% because most cells are fine; readiness answers go/no-go). Readiness = in-scope records with **no open defect** / in-scope records. A record is not ready when any deterministic COMPLETENESS/CORRECTNESS finding flags it, or when it is a duplicate that will be merged away (reviewer DUPLICATE verdict, the EXACT/PROBABLE recommendation, or a DUPLICATE from a group settled in an earlier run: `duplicate_detector` stats `settled_duplicate_rows`; the golden record and SIMILAR look-alikes stay ready). Records marked for deletion or dormant are **out of scope** and count neither way. Each table keeps its **worklist** (not-ready records with reasons, capped at `scorecard.max_worklist`) in the scorecard details, served at `GET /api/scorecard/not-ready?client_id=&table=&run_id=` (the `/api/scorecard` payload leaves it out). On acme: LFA1 69.6% ready vs DQ Index 97.1%, KNA1 59.8% vs 93.8%. **UI (deliberately low-key - kept for future use, not the current focus):** two small chips under "Promote Approved Skills", **DQ Index** and **Record readiness**, each opening a mini window (`initDqWindow`/`MINI_WINDOWS` in `app.js`; opening one closes the other; Esc or an outside click closes them). DQ Index: per object the four pillars + index. Record readiness: per object (expandable to tables) the readiness badge (`scorecard.readiness_bands`), not ready and out of scope, and a **View** link per table that opens the worklist in the detail modal with reasons as filters. There is no scorecard panel on the dashboard.

### Pipeline handoff (`explorer_agent/contracts.py`, `structural_profile.py`, `events.py`)

The agent sits in a pipeline: **Extract → structural profile → Mapping Agent → field/value mapping → DQ rules (this agent) → Cleansing**, with the **Metadata Repository** supplying SAP target domains. Structural profiling needs no column meaning, so it feeds the Mapping Agent. The DQ rules need meaning, so they consume the Mapping Agent's output. Four versioned contracts (pydantic models in `contracts.py`; schemas, examples and the review decisions in `explorer_agent/contract_schemas/README.md`, regenerated with `python -m explorer_agent.contracts`; MAJOR mismatch rejected, unknown fields ignored; v1.0 is still a draft revised in place):

- **OUT `sap-dm.structural-profile`** (`structural_profile.build_profile`, end of every run, validated before writing): per column the type (zero-padded numbers are `string` + `leading_zeros`), lengths, null/distinct stats, top-5 value shapes plus a ≥95% regex, `value_class`, `sensitivity`, and `domain`, meaning every distinct value **only for non-personal CATEGORICAL/FLAG columns** (≤ `handoff.max_domain_values`; personal = mapped name/address/contact/tax concept, or values that look like e-mail/IBAN/phone). With a target domain each value gets `target_status` VALID / MAPPED / UNMAPPED, and UNMAPPED values are the Value Mapping Agent's worklist. Written to `handoff/<client>/<run_id>/structural_profile.json` + `.latest.json` (gitignored), `GET /api/clients/{id}/handoff/structural-profile[?run_id=]`, schemas at `GET /api/handoff/schemas/{contract}`.
- **IN `sap-dm.field-value-mapping`** (`PUT /api/clients/{id}/handoff/field-mapping` → `client_data/<client>/field_mapping.json`, or `--mapping-file`) is step 0 of `column_mapping.resolve_mappings`. Each source column has **`targets[]`** (1-to-many for denormalized legacy files): the primary-key target, else the first, supplies the binding from the pack's `standard_columns`; `required` if any target is; references are translated back to source names, and a reference into the same source file is dropped (same record, not a link). The Mapping Agent sends **all** candidates with `confidence_score` 0–100, tier and explanation; this side applies `handoff.min_confidence` (default 90: APPROVED always, REJECTED never, PROPOSED from the score) and logs what it skipped (`metrics.mapping_candidates_below_threshold`). **Value mappings** are applied to all tables once (`column_mapping.apply_value_maps` → `rule_tables`), so the rules and survivorship check SAP values while duplicate matching keeps the originals.
- **IN `sap-dm.target-domains`** (Metadata Repository check tables; `PUT /api/clients/{id}/handoff/target-domains` → `target_domains.json`, or `--target-domains-file`): `column_mapping.attach_target_domains` puts `allowed_values` on columns whose (Mapping Agent or SAP-standard) target has a domain. `sap_rules._domain_rules` then reports **Invalid code** for values outside it, and the domain **replaces** the rare-code check for that column. On acme, a T052 domain found all 14 seeded invalid payment terms; the rare-code check found none.
- **OUT `sap-dm.pipeline-event` / job API:** `POST /api/jobs/run-profiling` (alias of `/run-explorer`) returns a `job_id`; `GET /api/jobs/{id}` adds `run_id` and `outputs` (profile and event URLs), parsed from `main.py`'s final `RESULT_JSON:` line. Every run appends `profiling.completed` (COMPLETED / PARTIAL) to the outbox `handoff/events.jsonl` (`events.publish`), served at `GET /api/handoff/events?client_id=&type=&after=`. Production replaces the transport (queue) behind the same documents.

Measured: renamed danawsiv with a Mapping Agent file → rule recall 0.80, the same as the SAP-named original. A denormalized vendor+company-code extract with 1-to-many targets → both tables' rules on one file, no self-orphans, the two low-confidence candidates skipped and reported.

### Cache fast path (`explorer_agent/cache_runner.py`)

Before invoking the planner for a column, `explore_table()` checks for existing approved skills for that exact table+column (`skill_registry.get_skills_for_table_column`). If found, the cached check code re-runs against fresh data and the planner LLM call is skipped entirely for that column (only the reflector may still run, unless `SKIP_REFLECTION_ON_CACHE_HIT` is set, in which case a rule-based heuristic replaces it). `explorer_agent/metrics.py` tracks LLM call counts and cache hit/miss counts per run to make these savings concrete.

### Privacy boundary

`explorer_agent/privacy_guard.py` (`sanitize_result_for_llm`) is the **last line of defense** before any locally-computed check result reaches an LLM: it withholds raw DataFrames/Series, masks string values (`profiler_primitives.mask_value`), and truncates long lists/strings. It is explicitly a best-effort heuristic, not a certified PII scanner. `explorer_agent/table_profiler.py` similarly uses an **allowlist** extraction from `ydata-profiling`'s raw JSON output — only explicitly named fields are pulled into the distilled profile sent to the planner LLM; anything not listed is dropped by default, since `value_counts_without_nan` etc. can contain raw values as dict keys even with `sensitive=True`.

`detail_code`/`detail_rows` output (row-level PII-bearing detail for confirmed findings) deliberately bypasses `privacy_guard` — it goes only to the local SQLite store (`finding_items` table) and the review UI, never to an LLM.

### Sandbox (`explorer_agent/sandbox.py`)

LLM-generated pandas code executes in a separate `multiprocessing` process (spawn context), with restricted builtins, a blocked-imports list (`os`, `sys`, `subprocess`, `socket`, `resource`, etc.), and (Unix-only) CPU/memory rlimits plus a wall-clock timeout with forced termination. One worker serves a batch of checks (`SandboxExecutor.session(context)`, used by `execute_checks`, the detail-row loop in `graph.py` and `cache_runner`): the tables are pickled and sent over a pipe once (no temp file of client data), `sandbox.load_timeout_seconds` covers start-up plus transfer, and `sandbox.timeout_seconds` applies to each check alone. Each check gets fresh globals and shallow copies of the frames under pandas copy-on-write, so it can't change the data the next check sees; a check that times out or crashes kills the worker and the next one starts a fresh worker. Module state (e.g. `pd.set_option`) is shared within a batch. At 1M rows six checks take ~4 s in total, where a process per check took ~8 s each. Documented as POC-grade isolation — "good enough to let an LLM experiment safely," not hardened against a determined adversary; harden further (containers/microVMs) before touching real client data.

### Review app (`review_app/`)

Two pages. **Page 1** (`static/index.html` + `setup.js`): pick a client from a typeahead of existing clients or "+ Add client" (created on its first upload), then upload that client's data dictionary and table CSVs. **Page 2** (`static/review.html?client=<client_id>` + `app.js`): the findings dashboard, fixed to that client — client, dictionary and tables are shown read-only in the header and the Run dialog; changing them means going back to page 1 ("Change client / data"). Missing/unknown `client` redirects to page 1.

**Client workspaces and dynamic tables.** Uploaded files live in `explorer_agent/client_workspace.py`'s per-client folder, `data.client_data_dir` (`client_data/<client_id>/`, gitignored raw client data, separate from `memory_store/` knowledge): the dictionary under its uploaded name, each table as `<TABLE>.csv`, and `workspace.json` metadata (rows, columns, upload time). Tables are not configured anywhere: the table name comes from the file name (`data_loader.table_name_from_filename`, `lfa1.csv` → `LFA1`) and `main.py` profiles every CSV under `--data-dir`, **searched recursively**, except the dictionary (`data_loader.discover_table_files`). A client can group tables by business object (`vendor-master/LFA1.csv`). The folder is presentation only: the table is still `LFA1`, and two files that map to the same table name abort the run. `client_workspace.save_table(..., subdir=)` and `seed_from_folder` preserve that layout. The loader reads every column as text and restores numeric measures using the dictionary's SAP data type (`apply_column_types`), because pandas inference strips the zero-padding from keys like LIFNR/MATNR. Uploads are the raw request body (`PUT /api/clients/{id}/dictionary?filename=…`, `PUT /api/clients/{id}/tables?filename=…`, no `python-multipart` dependency), streamed to a temp file, size-capped by `data.max_upload_mb`, then validated (CSV with rows; dictionary needs `Table`/`Field`/`Description`). Other endpoints: `POST /api/clients`, `GET /api/clients/{id}/workspace`, `DELETE /api/clients/{id}/tables/{table}`, `DELETE /api/clients/{id}/files` (page 1 **Clear all files**: removes every CSV in the client folder plus empty sub-folders and resets `workspace.json`; keeps `field_mapping.json`/`target_domains.json`, the episodic DB and `memory_store/clients/<client>`; 409 while a run is in progress), `GET /api/dictionary?client_id=` (tooltips from that client's dictionary). `POST /api/jobs/run-explorer` takes only `client_id` plus LLM options — the server builds `--client/--data-dir/--dictionary-file` from the workspace and refuses clients without a dictionary and at least one table. Duplicate detection works for any uploaded table because its matching rules are drafted by the LLM from that client's dictionary and column statistics on first sight of a schema, then reused from that client's memory (see "4-pillar classification and duplicate governance").

FastAPI app (`review_app/main.py`) serving a JSON API over `episodic_store` plus the promotion pipeline, with `review_app/static/` (vanilla HTML/CSS/JS) mounted last so `/api/*` routes take precedence. Non-API responses get `Cache-Control: no-cache` (middleware `revalidate_static_files`), because without it browsers heuristically cached `setup.js`/`app.js` and ran stale code against new HTML after an update. Key endpoints: `/api/runs`, `/api/findings` (filterable by `category`/`rule_scope`), `/api/findings/{id}/decision` (human approve/reject — the gate that `promotion.py` reads from), `/api/promote`, `/api/skills`, `/api/stats` (counts by category/rule_scope), plus per-row endpoints for reviewing individual `detail_rows`: `/api/findings/{id}/items`, `/api/finding-items/{id}/decision`, `/api/finding-items/{id}/verdict` and `/api/finding-items/{id}/autofill` (the `COMPLETENESS` auto-fix workflow), and duplicate governance (`/api/findings/{id}/duplicate-groups`, `/api/findings/{id}/duplicate-groups/{group_id}/verdict`), plus the background run endpoints (`/api/jobs/run-explorer` — accepts `duplicates_only` — `/api/jobs/current`, `/api/jobs/{id}`, `/api/jobs/{id}/stop`) — see "4-pillar classification and duplicate governance" above.

### Local LLM support (`explorer_agent/local_llms.py`)

`QwenCoderGGUFChatModel` wraps a local GGUF model (via `llama-cpp-python`) as a LangChain `BaseChatModel`, emulating structured output/tool-calling through llama.cpp's grammar-constrained JSON decoding rather than prompt-based coaxing. It supports exactly one bound tool/schema at a time. Used when `llm.provider` is `local`, the alternative to `ChatGoogleGenerativeAI` (Gemini) in `llm_providers.build_llms()`. This module deliberately does NOT import `llama_cpp` at module level (it's imported unconditionally by `llm_providers.py`) — the `Llama` instance is constructed only inside `llm_providers._get_local_llm()`.

`review_app/job_manager.py` runs `python -m explorer_agent.main` as a child process and keeps a 1000-line log tail in memory. It allows **one run at a time**, because everything shares one SQLite file and possibly the local LLM singleton. Job state is lost when uvicorn restarts.

## Invariants (do not break without an explicit decision)

1. **No raw data reaches an LLM.** Planner input is the allowlisted profile (`table_profiler.py`). Reflector input passes through `privacy_guard.sanitize_result_for_llm`. Duplicate-rule drafting and column mapping see only metadata plus `mask_value` samples (mapping also gets 1–2 character flag codes and value-overlap percentages). `detail_code`/`detail_rows` stay local. Any new LLM call site needs the same treatment. Adding a field to a prompt means adding it to an allowlist, never removing a filter.
2. **The LLM budget is bounded and independent of column count.** Each table costs 2 calls (planner + reflector), plus 1 duplicate-rule call and, for a non-SAP-standard layout, 1 column-mapping call the first time a client's schema is seen. Cache hits cost less. A feature that adds per-column or per-row LLM calls needs a stated reason and must show up in `metrics.py`. A failed check can add at most `max_repair_rounds` repair calls per table (default 1), and only when a check failed.
3. **Deterministic where business meaning isn't required.** Matching, execution and extraction are plain Python, and known SAP standards and anomaly checks are rule engines (`sap_rules.py`, `anomaly_rules.py`) written against concepts, not planner output. The LLM decides only *what a column means* (column mapping, duplicate roles) and *what to check beyond the standards*, and those decisions are persisted (column mappings, duplicate rules, skills) so later runs are free, auditable and correctable.
4. **Human gate before reuse.** Nothing becomes a skill without `APPROVED` status plus `reusable` plus `check_code` (`promotion.py`). Remembered duplicate decisions are per client, keyed by record fingerprint.
5. **Procedural JSON is the source of truth; Chroma is derived.** Only `chroma_store.py` imports `chromadb`.
6. **LLM-generated code runs only in `sandbox.py`**, never through `exec` in the main process.
7. **Configuration goes through `Config`.** Non-secrets live in `config.yaml` with an env override. Secrets live only in `.env`. Never hard-code paths or keys.

## POC vs production

This lists what is POC-grade today and what production would need. Use it to name gaps precisely. Don't close them unprompted.

| Area | Today (POC, verified in code) | Required before real client data / production |
|---|---|---|
| **Sandbox** | `multiprocessing` spawn, restricted builtins, import blocklist, wall-clock timeout. `resource` rlimits are Unix-only, so **on Windows (the dev machine) only the timeout applies**, with no memory or CPU cap. | Container or microVM isolation (gVisor/Firecracker), no network, read-only FS, enforced memory/CPU limits. Consider replacing free-form code with a check DSL or a vetted primitive library. |
| **Privacy** | Heuristic masking plus allowlisted profiles. Masked samples and the client dictionary are sent to hosted LLMs (Gemini). | A DPA and data-residency review per provider (or a local/VPC-hosted model), a real PII classifier, per-client opt-in to hosted LLMs, prompt/response audit logging, retention policy. |
| **Data at rest** | Raw client CSVs in `client_data/`, row-level PII in `finding_items` (SQLite). Both are gitignored and untracked, but still sit unencrypted on the local disk, and older commits contain the synthetic copies. | Encrypted storage outside the repo, per-client access control, retention and deletion (right-to-erasure) for `finding_items`/`record_data`. |
| **Review app security** | No authentication or authorization, CORS `*`, uploads capped by size only. Reviewer identity is a free-text name on duplicate decisions only (`finding_items.reviewer`, not authenticated); other verdicts record none. | SSO/OIDC, role-based access per client, reviewer identity plus an audit trail on every approve/reject/verdict (this is the governance gate), CSRF/CORS tightening, upload content scanning. |
| **Reliability** | Provider fallback chain, structured-output retries, failed tables skipped with exit code 1. One run at a time. Job state is in memory. Runs are started via REST with an async `job_id`, and completion is published as a `profiling.completed` event to a file outbox (`handoff/events.jsonl`). | A durable job queue (worker plus retries plus idempotent runs), resumable per-table progress, Postgres instead of SQLite for concurrent writers, pinned model versions. |
| **Evaluation** | Answer keys exist per synthetic client. `explorer_agent/evaluate.py` scores a run by hand (table + key + field matching); it is not run automatically and the keys themselves are incomplete. Keys are kept out of runs only by where they are stored (see "Data in this repo"). | A harness that scores findings and duplicate groups against answer keys (precision/recall per pillar and issue type), run on every prompt, model or rule change. Regression gate in CI. Track reviewer-approval rate as an online quality signal. |
| **Observability** | Python logging to console plus a rotating `logs/` file. `RunMetrics` counts LLM calls and cache hits per process. Per-request token counts and timings are stored (`llm_calls`, see "Token usage"); no prices. `runs.model` records the primary model only. | Structured logs with run/table/finding correlation IDs, LLM tracing (prompt version and cost per call on top of the stored token counts), dashboards for failure and retry rates. |
| **Maintainability** | No tests, linter or type checking. Additive `ALTER TABLE` migrations in `episodic_store._migrate`. Legacy fields remain (golden-record columns). | pytest around deterministic parts first (duplicate detector, rule compiler, loader typing, privacy guard). Ruff plus mypy, versioned migrations (Alembic), prompt versioning. |
| **Deployment** | Local `uvicorn --reload`, `.venv`, Windows-specific llama-cpp wheel. | A container image, config per environment, a secrets manager instead of `.env`, CI/CD, and a separate worker from the API. |

When a task touches one of these rows, prefer the POC-sized step that doesn't block the production path. Example: add a `reviewer` column now even without SSO, rather than building SSO.
